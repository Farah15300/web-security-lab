Permissions du Navigateur

Objectif: Comprendre comment demander et gérer les permissions utilisateur de manière éthique.

1. Permission Caméra

Code:

navigator.mediaDevices.getUserMedia({ video: true })
  .then(stream => {
    video.srcObject = stream;
    // ✅ Permission accordée explicitement
  })
  .catch(err => {
    // ❌ Permission refusée
  });

2. Géolocalisation

Code:

navigator.geolocation.getCurrentPosition(
  position => {
    const lat = position.coords.latitude;
    const lon = position.coords.longitude;
  },
  error => console.error(error)
);

3. Notifications

⚠️ Bonnes Pratiques:

  • Toujours expliquer POURQUOI vous demandez une permission
  • Demander les permissions au moment approprié (pas au chargement)
  • Respecter le refus de l'utilisateur
  • Permettre de révoquer les permissions facilement

XSS - Cross-Site Scripting

Définition: Injection de code JavaScript malveillant dans une page web.

Version VULNÉRABLE ⚠️

Problème: Le contenu est inséré directement sans sanitisation.

Version SÉCURISÉE ✅

Solution: Sanitisation/échappement du HTML avant affichage. 
text.replace(//g, '>')

Protection contre XSS:

  • Toujours échapper les données utilisateur
  • Utiliser Content Security Policy (CSP)
  • Ne jamais utiliser innerHTML avec des données non fiables
  • Utiliser textContent ou créer des éléments DOM

CSRF - Cross-Site Request Forgery

Définition: Forcer un utilisateur authentifié à exécuter des actions non désirées.

Version VULNÉRABLE ⚠️

Problème: Aucune vérification que la requête provient du site légitime.

Version SÉCURISÉE ✅

Solution: Token CSRF unique pour chaque session.

Protection contre CSRF:

  • Utiliser des tokens CSRF uniques
  • Vérifier l'origine des requêtes (Origin/Referer headers)
  • Utiliser SameSite cookies
  • Demander une re-authentification pour les actions sensibles

OWASP Top 10 (2021)

OWASP: Open Web Application Security Project - Les 10 risques de sécurité les plus critiques.

A01: Broken Access Control

Les utilisateurs peuvent accéder à des ressources non autorisées.

Exemple: Modifier l'ID dans l'URL pour voir le profil d'un autre utilisateur.

A02: Cryptographic Failures

Échec de protection des données sensibles (mots de passe, cartes bancaires).

Solution: Chiffrement, HTTPS, hashage des mots de passe.

A03: Injection

SQL, XSS, commande OS - injection de code malveillant.

Solution: Paramètres préparés, validation des entrées.

A04: Insecure Design

Failles de conception et d'architecture.

Solution: Threat modeling, design patterns sécurisés.

A05: Security Misconfiguration

Configurations par défaut, messages d'erreur verbeux.

Solution: Hardening, désactivation des fonctionnalités inutiles.

A06: Vulnerable Components

Utilisation de bibliothèques avec des vulnérabilités connues.

Solution: Mise à jour régulière, audit des dépendances.

A07: Authentication Failures

Failles dans l'authentification et la gestion de session.

Solution: MFA, rate limiting, gestion sécurisée des sessions.

A08: Software Data Integrity

Code et infrastructure sans vérification d'intégrité.

Solution: Signature de code, CI/CD sécurisé.

A09: Security Logging Failures

Logging et monitoring insuffisants.

Solution: Logs détaillés, alertes, SIEM.

A10: Server-Side Request Forgery (SSRF)

L'application récupère des ressources distantes sans validation.

Solution: Whitelist d'URLs, validation des entrées.
